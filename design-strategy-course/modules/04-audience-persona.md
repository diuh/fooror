# Модуль 4 — Аудиторія і прото-персона

> **Артефакт:** FigJam-канва прото-персони + чекліст джерел даних. Заповнений приклад — 1–2 прото-персони покупця UV.
> **Колір-тег:** 🟩 зелений (людина і її болі).

---

## Ціль модуля

Навчити збирати дані про аудиторію **без бюджету на дослідження** — з відкритих сигналів — і складати прото-персону, яка реально впливає на дизайн-рішення.

---

## Теорія

### Прото-персона vs персона на дослідженні

- **Персона** — будується на первинному дослідженні (інтервʼю, опитування, аналітика). Дорого й довго.
- **Прото-персона** — гіпотеза про користувача, зібрана з **уже наявних** сигналів і командних знань. Швидко, дешево, достатньо для старту більшості проєктів.

Прото-персони достатньо, коли: обмежений бюджет/час, ринок в цілому зрозумілий, треба вирівняти команду щодо «для кого робимо». Її головна чесність — **позначати, де факт, а де припущення**.

### Де брати дані без бюджету

| Джерело | Що витягуємо |
|---------|--------------|
| **Відгуки на конкурентів** (сайти, Google-мапи) | реальні болі, за що хвалять/лають |
| **Рев'ю на маркетплейсах** (Rozetka, Prom) | мова покупця, критерії вибору, страхи |
| **Коментарі в соцмережах / Instagram конкурентів** | заперечення, часті питання |
| **Форуми, Reddit, тематичні спільноти, Telegram-чати** | глибші болі й контекст використання |
| **Пошукові запити** (Google-підказки, Answer the Public) | що люди реально шукають, якими словами |
| **Дані клієнта** | існуючі покупці, CRM, статистика продажів |
| **Веб-аналітика** (якщо є сайт) | демографія, пристрої, поведінка |

Метод: збираємо **живі цитати** → групуємо в патерни (болі / цілі / барʼєри / тригери) → зводимо в персону.

### Структура прото-персони

- **Контекст** — хто це, ситуація, у якій купує.
- **Цілі / JTBD** — яку роботу «наймає» продукт зробити («мені треба…, щоб…»).
- **Болі** — що заважає, фруструє.
- **Барʼєри / заперечення** — чому може не купити (страх, недовіра, ціна).
- **Тригери** — що підштовхує до покупки.
- **Очікування від інтерфейсу** — що має бути, щоб їй було зручно й спокійно.

Кожен пункт — з позначкою `факт` (є доказ/цитата) або `гіпотеза` (припущення).

## Приклад UV: прото-персона покупця

На кейсі UV показуємо, як із відкритих сигналів (відгуки, коментарі, запити в ніші) складається персона, і як кожен інсайт веде до рішення в інтерфейсі:

| Блок персони UV | Приклад наповнення | Наслідок для дизайну |
|---|---|---|
| Контекст | купує [товар] онлайн, порівнює кілька магазинів перед рішенням | зручне порівняння, чіткий каталог |
| JTBD | «хочу швидко знайти потрібне й бути впевненим у якості» | сильна картка товару, фільтри, докази якості |
| Болі | важко зорієнтуватись в асортименті, страх «не те/підробка» | UX каталогу (POD), блок довіри/відгуків (POP) |
| Барʼєри | недовіра до незнайомого магазину, питання доставки/повернення | видимі гарантії, умови НП, месенджери для звʼязку |
| Тригери | зрозуміла ціна, швидка відповідь, приємний бренд | акценти на ціні/CTA, онлайн-чат, брендова подача (POD) |
| Очікування від UI | зрозуміла навігація, мобільна зручність, швидкий контакт | мобільний-first, месенджери у видимій зоні |

> **Ключове для студента:** дивись праву колонку — вона зʼєднує персону з POD/POP з М2. Болі підказують, які POP обовʼязкові, а які болі можна закрити краще за всіх → підсилити POD.

## Твій шаблон

**Канва прото-персони** (6 блоків вище), у кожному блоці два стовпці: `зміст` і `факт/гіпотеза`. Плюс третій наскрізний стовпець — `інсайт → наслідок для дизайну`.

**Чекліст джерел даних** — список зон збору (відгуки, рев'ю, коментарі, форуми, запити, дані клієнта, аналітика) з полем «звідки взяв цитати» — щоб персона спиралась на докази, а не на уяву.

**Банк цитат** — окрема зона, куди студент складає живі фрази користувачів перед синтезом (важливо: спершу цитати, потім висновки, не навпаки).

## AI-кроки

### AI-крок 1 — синтез патернів із цитат

**Промпт:**
```
Ось живі цитати/відгуки користувачів у ніші [ніша]: [встав цитати].
Згрупуй їх у патерни: цілі (JTBD), болі, барʼєри/заперечення, тригери покупки.
Наводь підтвердження цитатою. Де роблю припущення без доказів — познач [ГІПОТЕЗА].
```
**Приклад на UV:** AI зводить розсипані відгуки в 3–4 повторювані болі й формулює JTBD мовою покупця.
**Застереження:** годуй AI **реальними** цитатами, а не проси «вигадати аудиторію». Інакше отримаєш правдоподібну фантазію.

### AI-крок 2 — чернетка прото-персони

**Промпт:**
```
На основі цих патернів: [патерни] склади прото-персону за структурою:
контекст, JTBD, болі, барʼєри, тригери, очікування від інтерфейсу.
Кожен пункт познач [ФАКТ] або [ГІПОТЕЗА]. Додай колонку «наслідок для дизайну».
```
**Застереження:** персона — робочий інструмент, не «паспорт з іменем і фото». Не давай AI прикрашати її вигаданими деталями.

### AI-крок 3 — генерація JTBD

**Промпт:**
```
Сформулюй 3–5 Jobs To Be Done для аудиторії [опис] у форматі
«Коли [ситуація], я хочу [мотив], щоб [результат]». На основі болів: [болі].
```
**Застереження:** обери ті JTBD, що справді драйвлять покупку у твоїй ніші.

### AI-крок 4 — стрес-тест персони

**Промпт:**
```
Ось моя прото-персона: [персона]. Виступи скептиком: які припущення не підкріплені?
Де я міг спроєктувати на користувача власні уподобання? Які болі я, ймовірно, пропустив?
Що варто перевірити перед тим, як спиратись на цю персону в дизайні?
```
**Застереження:** результат — список ризиків, а не привід усе переробити. Пріоритезуй сам.

## Чеклист готовності модуля

- [ ] Дані зібрано щонайменше з 3 різних джерел (не з голови).
- [ ] Є банк живих цитат, з якого виведені висновки.
- [ ] Кожен блок персони позначено `факт` / `гіпотеза`.
- [ ] Кожен ключовий біль звʼязано з наслідком для дизайну (і, де можливо, з POD/POP).
- [ ] Персону прогнано через стрес-тест на непідкріплені припущення.
